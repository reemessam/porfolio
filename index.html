Case studies

Detecting structured cash transactions

FlairsTech · SmartCheck, SAR/CTR compliance module

The problem

SAR and CTR reporting exists to catch structuring — cash activity broken into pieces to stay under FinCEN's reporting thresholds. SmartCheck aggregated a customer's transactions over rolling time windows to catch that pattern. The complication: customers could also pay down part of an aggregated transaction by card, and the system had no record linking a given card payment to the specific transaction it applied against. That made it genuinely hard to subtract the card-paid portion before comparing the aggregate to the threshold — a transaction that was partly settled by card risked still being counted as if it were fully cash.

What I'd change

Looking back, I'd model payments as their own first-class record from the start — every payment, cash or card, linked explicitly to the transaction or aggregate it settles. That way the amount still outstanding in cash, which is the only figure that actually matters for SAR/CTR, is something you compute directly rather than something you have to infer after the fact.



Ad hoc segmentation across 50M subscribers

Orange Innovation Egypt · Customer Value Management (CVM)

The problem

Marketing needed to build customer segments on the fly — arbitrary, changing combinations of criteria across a 50-million-subscriber base — for campaign and offer targeting. Hardcoding a new filter every time someone needed a new combination wasn't sustainable.

How it worked

I built a dynamic query builder in Java that composed the underlying SQL using CTEs, so filter criteria could be layered and combined without re-scanning the full subscriber table for each one. That builder sat behind REST APIs used by the campaign tooling, with BDD acceptance tests covering the segmentation logic end to end.



Cutting image-retrieval latency

Orange Innovation Egypt · Digital Agricultural Clinic

The problem

The clinic app diagnosed plant disease from photos, which meant every request needed an image back to the client fast. Retrieving those images through the S3 SDK on the backend was slow and became a real bottleneck — the app server was pulling the full image from S3 before it could even start sending it on, adding latency and load for bytes it didn't actually need to touch.

How I'd solve it

Generate a presigned URL from S3 and hand that to the client directly, instead of routing image bytes through the app server. The client fetches the image straight from S3, and the app server's job shrinks to issuing a short-lived URL — out of the data path entirely, which is where most of the latency and load was coming from.
